# RSI gap audit — 16 September 2026

This is a targeted check of the project's research claims against primary papers, not an exhaustive novelty search. “Still open” below means that the papers checked did not answer the specified comparison. It does not prove that no paper does.

## The field has moved closer to the proposed experiment

| Work | Result relevant to this project | What it leaves unresolved |
| --- | --- | --- |
| [CURE (2025)](https://arxiv.org/html/2506.03136) | Jointly improves a coder and unit tester without ground-truth code. Coder reward uses ground-truth tests. Its ablations include coder-only optimization and supervised fine-tuning; the paper describes these as alternatives, without a clean frozen-tester intervention. | Its coder-only result does not isolate H1. It does not establish a frozen-versus-online tester comparison at matched solver updates **and** matched total compute, with independent-oracle one-shot pass@k curves across training. |
| [ReVeal (2025)](https://arxiv.org/html/2506.11442) | Trains generation and self-verification together, using golden solutions to filter tests during training, and reports pass@k through 128 on LiveCodeBench. | Its multi-turn generation/verification policy changes several things at once. The reported pass@k gain does not isolate the effect of updating the tester from the effects of iterative tool feedback and its training objective. |
| [ACE (2026)](https://arxiv.org/html/2605.16299) | Co-optimizes a solver and adversarial test generator; its ablation replaces the optimized adversary with random tests at a matched stated compute budget. It reports code pass@k and out-of-distribution gains. Solver selection also uses ground-truth tests; generated adversarial inputs are scored for normal execution rather than output correctness. | This makes “trained tests improve code” an established claim. The remaining question concerns a *specific* frozen-verifier control, independent oracle quality, and whether extra tester compute beats extra solver compute. |
| [MIST-RL (2026)](https://arxiv.org/abs/2603.01409) | Uses incremental mutation reward to train a test writer and improves downstream code reranking. | Mutation-based tester training is prior art. It does not by itself establish the effect of online tester updates on a jointly trained solver. |
| [SPADE (2026)](https://arxiv.org/abs/2608.19197) | Trains an adaptive environment designer alongside a reasoning agent. Document grounding and environment memory matter to its results. | Adding a learned proposer is no longer a novel contribution on its own. A measured allocation among proposing, solving, and evaluation, or an independently audited grounding requirement, could still be distinct. |

**Revised H1 claim.** ACE's optimized-versus-random test comparison at stated matched compute makes H1 **partly covered**, not simply open. ACE uses a single model and a random-test control rather than a frozen-tester control. Its adversarial test signal detects execution failures, while solver selection also uses ground-truth tests with oracle outputs. CURE is related joint-training work, but its coder reward is based on ground-truth tests and its reported ablations do not isolate tester updating. A defensible question is: *At a fixed solver training schedule, does updating a separate test writer improve held-out code correctness and one-shot pass@k over freezing that writer? At fixed total compute, does that gain exceed spending the same extra compute on the solver?* The targeted papers above do not appear to answer both comparisons together. This is an inference from their reported designs, subject to a fuller related-work search.

## Measurement problems in the current brief

1. **The proposed solver-verifier “gap sign” compares unlike quantities.** Solver pass@1 and tester mutation score have different denominators and meanings. Measure both roles on the same held-out task/solution pairs: solver correctness under an independent oracle, and tester false-accept/false-reject rates on balanced correct and incorrect solutions. Report performance across model sizes using these matched definitions.
2. **Mutation score is an intermediate reward, not a validity guarantee.** A 2026 [replication study on Java projects](https://arxiv.org/html/2607.22880) finds that mutation score's relationship to real-bug detection depends on whether the supplied code is actually bug-free. When a buggy implementation is shown to an LLM, generated tests can assert its wrong behavior. Transfer to this project's code distribution remains to be tested. A proposer-written reference that merely executes may be wrong relative to its specification. Audit reference implementations independently and measure detection of held-out real bugs as well as held-out mutants.
3. **The current proxy-reality gap risks comparing different task distributions.** On the *same held-out task and solver samples*, score each sample under the generated test suite and the trusted oracle. Report false accepts and false rejects, plus their change over training. A difference between proxy pass rate on training tasks and oracle pass rate on separate held-out tasks mixes verifier error with distribution shift.
4. **H2 mixes two interventions.** Changing the fraction of trusted-test tasks changes access to external information. Deliberately corrupting a verifier changes its error rates. Run these as separate experiments (or a small factorial design); record realized false-accept and false-reject rates. A nominal corruption percentage is not a measured grounding rate.
5. **A short fitted curve is weak evidence for a ceiling.** The verifier-convergence result in [Yi et al.](https://arxiv.org/abs/2510.16657) is proved in a linear-regression setting and illustrated in other models; it is a useful hypothesis here, not a general ceiling theorem for code self-play. Treat fitted asymptotes as exploratory until multiple runs visibly plateau and alternative curve families agree. Report measured performance at fixed compute as the primary result.
6. **Pass@k needs a clean inference protocol.** Evaluate raw, one-shot solver samples without tester assistance to measure model coverage. Separately evaluate tester-guided selection or multi-turn repair at a matched inference budget. ReVeal shows why these can diverge. Use paired tasks, fixed decoding settings, enough samples for the largest k, and uncertainty intervals across tasks and training seeds. [A free-verifier study](https://arxiv.org/abs/2606.07856) found a pass@8 versus pass@64 crossover, so low-k gain alone is insufficient.

## Minimum experiment that answers the sharpened H1

Run a small pilot first to validate task oracles, mutant quality, sample counts, and budget accounting. Freeze the task stream and held-out evaluation before comparing arms.

| Arm | Tester | Solver | Purpose |
| --- | --- | --- | --- |
| A | Frozen at the same starting checkpoint | Fixed number of updates | Baseline at matched solver exposure |
| B | Updated online on mutation-based reward | Same solver updates as A | Effect of tester updates, with extra total compute |
| C | Frozen | Uses the additional compute B spent on tester updates | Practical compute-allocation comparison |

Keep base weights, task order, code samples per task, test execution allowance, prompts, optimizer settings, and evaluation checkpoints aligned where the intervention permits. Count **all** relevant compute: proposer and tester inference, mutation execution, solver rollouts, training, and reference validation. If task generation is adaptive, hold it fixed for this first comparison; otherwise the arms no longer isolate verifier training.

Primary outcome: independent-oracle pass@1 and the one-shot pass@k curve at fixed total compute. Secondary outcomes: pass@k at matched solver updates, tester false accepts/rejects, real-bug detection, held-out mutation score, proxy/oracle disagreement, task diversity, and entropy. Use at least three training seeds as the brief already proposes; estimate uncertainty over both tasks and seeds. Predeclare what result would count as meaningful before inspecting the final holdout.

The existing random-reward control remains valuable. [Shao et al.](https://arxiv.org/abs/2506.10947) found that random rewards can improve Qwen math performance under GRPO, whereas the effect did not generalize to other model families. A Qwen-only positive result is especially hard to interpret without that control and an independent model family.

## RSI claims need a narrower vocabulary

This project measures improvement of a solver, tester, and possibly task proposer inside a designed training loop. It does **not** yet measure an agent improving the algorithm that creates its successor. [AI4AI-Bench](https://arxiv.org/abs/2608.20318) isolates changes to training algorithms and finds that most agent submissions do not change the learning procedure at all. [Recursive Harness Self-Improvement](https://arxiv.org/abs/2607.15524) shows a different route, improving task-specific harnesses with a fixed model. These works support keeping three outcomes separate: better model weights, better surrounding procedure, and improvement of the improvement algorithm itself. The last is the strongest RSI claim and needs a transfer or inheritance test across generations.

## Priority after this audit

1. **Validate the measuring instrument.** Build independently checked references and a paired tester confusion matrix; test whether mutation score tracks real-bug detection on this code distribution.
2. **Run the three-arm H1 pilot.** This is the clearest small-lab contribution if the independent oracle and budget accounting work.
3. **Study trusted-signal fraction and verifier corruption separately.** Only proceed after the tester's real errors are measurable.
4. **Then allocate proposer/solver/tester compute.** SPADE makes adaptive task generation credible prior art, so the value here is a controlled allocation result.
5. **Keep selection-endogenous pooling and joint staleness/task drift as secondary tracks.** This audit did not recheck their complete literatures; retain them as hypotheses rather than confirmed empty spaces.
